# 03. GitHub 버전 관리·복구 절차

**중요:** GitHub에 올린 코드의 이력(커밋)과 게임 속 저장 데이터는 다른 것입니다.

## 익숙해져야 할 개념

| 개념 | 역할 | 예시 |
|---|---|---|
| Repository(저장소) | 프로젝트 전체 보관 | `little-orchard` |
| Commit(커밋) | 변경 지점 저장 | `feat: 사과 수확 구현` |
| Branch(브랜치) | 분리된 작업 공간 | `feature/apple-harvest` |
| Pull request(PR) | 변경 검토 후 합치기 | 기능을 `main`에 합치기 |
| Tag(태그) | 특정 버전 고정 | `v0.1.0` |
| Release(릴리스) | 유저에게 보여줄 버전 기록 | `v0.1.0 첫 플레이 버전` |
| GitHub Actions | 테스트와 배포 | main 업데이트 시 검사/배포 |

## 초보자를 위한 가장 간단한 규칙

1. `main`은 **현재 안정적으로 돌아가는 버전**으로 취급.
2. 새 기능은 `feature/fruit-growth`, `feature/customer-path` 같은 새 브랜치에서 수정.
3. 커밋은 **의미 있는 작은 단위**로. 하루 1번보다 기능이나 실험의 완료 지점 기준이 좋음.
4. `npm run test`와 `npm run build`를 통과한 뒤에만 `main`에 합치기. 모바일 화면도 확인.
5. 정상 동작하는 중요한 시점에 `v0.1.0`, `v0.2.0`처럼 태그와 릴리스 기록.
6. AI에게 수정 맡기기 전 **현재 상태 커밋**. 문제 발생 시 `git revert`로 안전하게 되돌리는 방식을 우선.
7. `.env`, 비밀번호, API 키, 개인 데이터는 절대 저장소에 넣지 않기.
8. `node_modules/`, `dist/`는 Git에 올리지 않음(`.gitignore`). 하지만 `package-lock.json`은 **반드시 올림**.

## 버전 이름 제안

- `v0.1.0` 최초 플레이(수확→진열→판매)
- `v0.2.0` 아트/애니메이션과 손님 개선
- `v0.3.0` 확장 및 편의 기능
- `v1.0.0` 충분한 테스트를 거친 첫 공개 버전

중간 작은 수정은 `v0.1.1`, `v0.1.2`처럼 늘립니다. **이 숫자는 예시일 뿐**입니다.

## 자주 쓰는 Git 명령 (Codex에 맡겨도 됩니다)

```bash
git status
git switch -c feature/apple-harvest
git add .
git commit -m "feat: add apple harvesting"
git push -u origin feature/apple-harvest
# GitHub에서 PR 검토 후 main에 병합

git switch main
git pull --ff-only
git tag v0.1.0
git push origin v0.1.0
```

## 잘못된 기능을 복구할 때

- **아직 main에 합치지 않았다면**: 해당 브랜치에서 수정/폐기하면 안정 버전은 그대로입니다.
- **main에 합쳤다면**: 문제 커밋을 찾고 `git revert <커밋해시>`로 **새로운 되돌리기 커밋**을 만드는 게 안전합니다. (협업 브랜치에 `git reset --hard` + 강제 푸시를 무턱대고 하지 마세요.)
- **사이트 배포에 문제가 났다면**: 정상 릴리스의 커밋으로 되돌린 후 Actions 재배포.
- **저장 데이터가 깨졌다면**: Git 버전을 되돌려도 사용자 브라우저의 세이브는 자동 복구되지 않습니다. 저장 포맷 테스트와 백업/내보내기가 별도 필요합니다.

## 버그 보고 양식

어느 기기/브라우저인지, 무슨 행동을 했는지, 예상 결과, 실제 결과, 오류 화면, 콘솔 오류, 재현 빈도를 적습니다. 코드 수정보다 재현이 먼저입니다.

## 추천 설정

혼자 개발하더라도 가능하면 `main` 직접 수정을 줄이고 PR을 사용하세요. 중요한 단계가 되면 브랜치 보호 규칙으로 main 변경에 테스트 통과를 요구할 수 있습니다. 권한/요금제에 따라 적용 가능 여부가 다릅니다.
